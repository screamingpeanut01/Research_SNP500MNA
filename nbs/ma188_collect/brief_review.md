## 역할

너는 **독립 검토자**다. 다른 에이전트가 수집한 거래 기록을 한 건씩 검토한다. 수집 기록에 적힌 내용을 믿지 말고, 출처를 직접 다시 열어 확인한다. 목표는 연구에 쓸 수 있을 만큼 신뢰할 수 있는 기록이다.

먼저 `SP/brief_collect.md`를 끝까지 읽는다. 항목 정의, 분류 기준, 근거 형식, 도구 사용법이 모두 거기에 있다. 검토도 같은 기준을 따른다.

## 입력

- `SP/batches/<묶음>.json`: 원자료의 거래 정보
- `SP/records/<deal_id>.json`: 수집 기록 (묶음의 거래마다 하나)

## 검토 깊이

유닛 파일의 `depth`가 검토 깊이를 정한다. `brief_collect.md` 0절의 토큰 절약 규칙은 검토에도 그대로 적용된다.

- `full` (전수 검토, 1천만 달러 이상·금액 의심 거래): 아래 "거래 한 건마다 할 일" 1~5를 모두 한다. 도구 호출 예산은 거래 하나에 **30회 안팎**.
- `light` (핵심 항목 검토, 1천만 달러 미만 거래): 다음만 한다. 도구 호출 예산은 거래 하나에 **12회 안팎**.
  1. `subtype_chk`, `pre_incorp_chk`, `status_chk`를 정의대로 다시 판정한다.
  2. `value_chk_local`·`value_chk_usdmm`, `announce_date_chk`, `deal_to_assets_pct`, `impairment`, 실적 숫자(`target_rev_*`, `target_op_*`)를 그 값의 근거 문서에서 대조한다. 근거 문서는 캐시나 grep으로 필요한 줄만 본다.
  3. 근거 없는 값이 있으면 고치거나 `미확인`으로 바꾼다.
  4. 빠진 사건을 찾는 독립 검색은 하지 않는다. 단, `post_events_summary`가 비어 있거나 `미확인`이면 합병·매각·청산 여부를 한 번만 검색한다.

## 거래 한 건마다 할 일 (순서대로)

1. **근거 대조**: `evidence`의 URL과 문서를 모두 직접 연다. 각 근거가 `sheet`의 해당 값을 실제로 뒷받침하는지 확인한다. 특히 다음을 본다.
   - 숫자: 단위(원·천원·백만원·억원), 회계연도, 별도/연결, 자릿수
   - 날짜: 발표일·완료일·이벤트 날짜가 문서와 같은지
   - 인용: `purpose_quote`와 `earnings_call_note`의 인용이 원문과 같은지
   - 열지 못한 URL은 다른 경로(같은 문서의 다른 주소, DART 접수번호)로 다시 시도한다.
2. **근거 연결**: `미확인`·`해당 없음`이 아닌 모든 값에 근거 행이 있는지 확인한다. 근거 없는 값은 근거를 찾아 넣거나 값을 고친다.
3. **빠진 것 찾기**: 독립적으로 검색해 빠진 사건과 수치를 찾는다.
   - 인수 전: 이전 투자 유치, 그룹의 이전 지분, 이전 소유주 변경, 인수 직전 실적
   - 인수 후: 합병, 사명 변경, 추가 취득, 매각, 상장, 청산, 손상차손, 대표 교체(현재까지)
   - 실적: 인수 전 2개 연도, 인수 후 2개 연도와 최근 연도 중 빠진 해
   - 어닝콜·IR 언급
   - `미확인`으로 남은 열마다 **서로 다른 경로로 최소 두 번** 더 찾아본다.
4. **분류 재판정**: `subtype_chk`, `pre_incorp_chk`, `status_chk`, `is_core`를 정의에 따라 다시 판단한다. 단계적 경영권 인수 여부, 편입 시점, 같은 인수가 여러 행으로 기록됐는지를 특히 본다.
5. **묶음 안 일관성**: 같은 대상회사 계보의 거래끼리 날짜, 지분율, 사건 서술이 서로 맞는지 본다.

## 출력

거래마다 `SP/records/review_<deal_id>.json`을 UTF-8로 쓴다. **수집 기록 파일(`<deal_id>.json`)은 고치지 않는다.**

```json
{
 "deal_id": "K009",
 "review_status": "수정",
 "review_note": "확인한 것: ... / 고친 것: target_op_post (2017 영업이익 단위 오류, 천원→백만원) ... / 남은 의문: ...",
 "corrections": {"target_op_post": "고친 값 전체"},
 "evidence_add": [{"field": "...", "phase": "...", "event_date": "...", "event_type": "...", "content": "...",
                   "url": "...", "doc_type": "...", "doc_date": "...", "doc_id": "..."}],
 "evidence_drop": ["근거로 쓸 수 없는 행의 url"]
}
```

- `review_status`
  - `통과`: 고칠 것이 없다
  - `수정`: 고쳤다. 고친 값마다 근거를 `evidence_add`에 넣는다
  - `보류`: 출처끼리 충돌하거나 확인할 수 없어 판단을 미룬다. 이유를 `review_note`에 쓴다
- `corrections`에는 바꿀 열의 **새 값 전체**를 넣는다(차이만 쓰지 않는다). 열 이름은 `brief_collect.md` 3절의 열만 쓴다. `collect_status`도 고칠 수 있다.
- `review_note`는 "확인한 것 / 고친 것과 이유 / 남은 의문" 순서로 쓴다. 무엇을 열어 봤는지 구체적으로 적는다.
- 쓰고 나서 JSON이 파싱되는지 확인한다.

## 금지 사항

`brief_collect.md` 8절과 같다. 특히 **브라우저 도구(`mcp__Claude_Browser__*`, `mcp__claude-in-chrome__*`)를 쓰지 않는다.** 사용량 한도로 중간에 멈출 수 있으므로 **거래 하나를 마칠 때마다 그 review 파일을 바로 쓴다.** 저장소 파일을 고치지 않고, 쓰기는 `SP/records/review_*.json`과 `SP/work/review_<묶음>/`에서만 한다.
